Namespaces ⎕NS

The utility of a language as a tool of thought increases with the range of topics it can treat, but decreases with the amount of vocabulary and the complexity of grammatical rules which the user must keep in mind. Economy of notation is therefore important. --Kenneth E. Iverson Iverson, 1980

If you come from another programming language, Dyalog’s namespaces will appear confusing: they’re used both as an associative array (dict) and as a hierarchical code-organisational construct -- you know, an actual namespace. Dyalog describes namespaces like so:

Namespace is a (class 9) object in Dyalog APL. Namespaces are analogous to nested workspaces.

No, that doesn’t mean anything to me either. In fact, the code-organisational aspect of APL namespaces are similar in spirit to those found in C++:

Namespaces provide a method for preventing name conflicts in large projects. Symbols declared inside a namespace block are placed in a named scope that prevents them from being mistaken for identically-named symbols in other scopes.

except that Dyalog’s namespaces don’t obey the time-honoured name scoping rules C++ programmers expect. Sadly.

Namespaces as dicts¶

A namespace in Dyalog APL can be thought of as a dictionary mapping keys to values. Values are accessed by the dot notation that should feel familiar for those of you who know an object-oriented language like JavaScript or Python.

There are many ways to construct namespaces in Dyalog APL. The simplest is perhaps to use APLAN,

⊢ ns_ ← (
  author: 'Gödel, Kurt'
  title: 'On Formally Undecidable Propositions of Principia Mathematica'
  booktitle: 'Kurt Gödel: Collected Works, Volume I'
  publisher: 'Oxford University Press'
  year: 1931
  note: 'trans. Jean van Heijenoort, publ. 1986'
)
Loading...

Namespaces don’t display, and APLers see this as a feature (and if you think of the other use of namespaces in APL -- actual namespaces -- you can probably see why). The namespace notation in APLAN is very close to that of many other languages, e.g. Python:

~/work/notebooks/learnapl/contents [20] $ python
Python 3.11.3 (main, Apr 28 2025, 10:54:41) [Clang 16.0.0 (clang-1600.0.26.6)] on darwin
Type "help", "copyright", "credits" or "license" for more information.
>>> {
...   'author': 'Gödel, Kurt',
...   'title': 'On Formally Undecidable Propositions of Principia Mathematica',
...   'booktitle': 'Kurt Gödel: Collected Works, Volume I',
...   'publisher': 'Oxford University Press',
...   'year': 1931,
...   'note': 'trans. Jean van Heijenoort, publ. 1986'
... }
{'author': 'Gödel, Kurt', 'title': 'On Formally Undecidable Propositions of Principia Mathematica', 'booktitle': 'Kurt Gödel: Collected Works, Volume I', 'publisher': 'Oxford University Press', 'year': 1931, 'note': 'trans. Jean van Heijenoort, publ. 1986'}
>>>

Python does have a nice display form for dicts -- as they are dicts, not namespaces masquerading as dicts.

You may have spotted that we added an underscore at the end of our namespace name. This is just a stylistic convention; an indication that “something goes here”. It completes our informal house style guidelines for names we use in this book:

Name styleType
Leading uppercaseFunction
Leading underscore, first letter uppercaseMonadic operator
Leading underscore, first letter uppercase, trailing underscoreDyadic operator
Leading lowercase, trailing underscoreNamespace
Leading lowercaseArray

We can view our namespace by converting it to JSON (we’ll cover Dyalog’s ⎕JSON in more depth in the next chapter):

NSShow ← 1∘(⎕JSON⍠'Compact' 0)
NSShow ns_
Loading...

Namespace members are names, not strings¶

One important distinction between our namespaces and the keys in an actual dict is that Dyalog APL’s namespace keys are APL names, not strings. This comes back to the central duality. A “key” in a namespace is really an APL variable, and so it can sometimes help to think of a namespace as an object instance. This is perhaps clearer if we look at a different way of constructing namespaces, using ⎕NS.

ns_ ← ⎕NS ⍬ ⍝ Construct empty anonymous namespace
ns_.author ← 'Gödel, Kurt'
ns_.title ← 'On Formally Undecidable Propositions of Principia Mathematica'
ns_.booktitle ← 'Kurt Gödel: Collected Works, Volume I'
ns_.publisher ← 'Oxford University Press'
ns_.year ← 1931
ns_.note ← 'trans. Jean van Heijenoort, publ. 1986'

NSShow ns_
Loading...

If we think about the namespace interpretation of the namespace (a phrase that sounds more vacuous every time I type it), it’s not a big leap to see that we can make use of APL’s normal assignment rules here:

values ← (
    'Gödel, Kurt'
    'On Formally Undecidable Propositions of Principia Mathematica'
    'Kurt Gödel: Collected Works, Volume I'
    'Oxford University Press'
    1931
    'trans. Jean van Heijenoort, publ. 1986'
)

ns_ ← ⎕NS ⍬
ns_.(author title booktitle publisher year note) ← values

NSShow ns_
Loading...

In Python, dict keys can be anything that’s hashable, but in Dyalog APL, namespace members must have valid APL names -- they are identifiers. Dyalog jumps through hoops in order to smooth over this wrinkle. We’ll see more about this when we introduce ⎕JSON properly, but JSON, of course, assumes that keys are values:

NSShow ns_ ← 0⎕JSON'{"First name": "Kurt", "Last name": "Gödel"}'
Loading...

So far, so 100% expected. But ⎕JSON does something under the covers, which we can uncover by actually requesting the keys:

]MAP ns_
Loading...

⎕JSON seamlessly mangles and un-mangles keys to be valid namespace members. Thus, to access a single key, we need to do

ns_.⍙First⍙32⍙name
Loading...

Getting and setting values with ⎕VGET and ⎕VSET¶

Even accepting the name vs value quirk for keys, using namespaces as dicts in Dyalog used to be both clunky and slow, but in the v20 release of Dyalog APL, several core changes made it much more ergonomic and performant. We’ve already seen how APLAN makes it very natural to compose dict literals. Let’s first show some of the problematic aspects. If we have a vector of keys and a vector of values, how can we associate those in a namespace? Prior to v20, we’d have to construct assignments as strings that were then evaluated inside the namespace:

ns_ ← ⎕NS ⍬

keys ← (
    'author'
    'title'
    'booktitle'
    'publisher'
    'year'
    'note'
)

values ← (
    'Gödel, Kurt'
    'On Formally Undecidable Propositions of Principia Mathematica'
    'Kurt Gödel: Collected Works, Volume I'
    'Oxford University Press'
    1931
    'trans. Jean van Heijenoort, publ. 1986'
)

⍝ Dyalog APL pre-v20
ns_ {⍺.{⍎⍺,'←⍵'}¨/⍵} keys values 
⍝   │  ││    │ └───────────────── For every key-value pair,
⍝   │  │└────┴─────────────────── the string '{key}←{val}' is
⍝   │  └─────────────────────────    ...evaluated
⍝   └────────────────────────────    ...inside the namespace

NSShow ns_
Loading...

Works, sure. But if you think that is ugly, unsafe and inefficient, that’s because it is. Imagine if a key contained ⎕OFF⋄.

Fortunately, there is now a nicer, safer and faster way, using the system function ⎕VSET:

ns_ ← ⎕NS ⍬
ns_ ⎕VSET (↑keys) values  ⍝ Dyalog v20+
NSShow ns_
Loading...

Why the Mix you say? Well, that’s so that ⎕VSET can also take a zipped list of key-value pairs:

ns_ ← ⎕NS ⍬

⍝ A subset of the data...
ns_ ⎕VSET ('author' 'Gödel, Kurt' ⋄ 'title' 'On Formally Undecidable Propositions of Principia Mathematica')
NSShow ns_
Loading...

The Mix in the first instance is necessary in order for ⎕VSET to be able to distinguish between the two different forms of its right argument.

Getting values as strings suffered the analogous problem to the setting which we outlined above. ⎕VSET has a sibling function, ⎕VGET, that solves that for us:

keys ← 'author' 'title'

ns_ ⎕VGET keys
Loading...

⎕VGET has a very nice feature built in, similar to how Python’s .get() method works on dicts -- we can specify default values to be returned if a key isn’t found:

ns_ ⎕VGET ('author' '-- no author given --' ⋄ 'title' '-- no title given --' ⋄ 'year' '-- no year given --')
Loading...

For a single key with default, we need to enclose the right argument:

ns_ ⎕VGET ⊂'year' '-- no year given --'
Loading...

The combination of APLAN and ⎕VSET|VGET has some powerful, but not immediately obvious consequences. An empty parenthesis pair is now APLAN for “new namespace”. That means we can say

keys ← 'artist' 'country' 'language' 'genre'
vals ← 'Drake' 'Canada' 'English' 'Hip-Hop'

ns_ ← ()⎕VSET(↑keys)vals

NSShow ns_
Loading...

Arrays of namespaces¶

Namespace references -- like any other APL type -- can be arranged in arrays, and this has some neat consequences. For example, dot-access applies to an array of any rank:

jazz ← (
  (title: 'Kind of Blue'              ⋄ artist: 'Miles Davis'     ⋄ year: 1959)
  (title: 'The Shape of Jazz to Come' ⋄ artist: 'Ornette Coleman' ⋄ year: 1959)
  (title: 'A Love Supreme'            ⋄ artist: 'John Coltrane'   ⋄ year: 1965)
  (title: 'Mingus Ah Um'              ⋄ artist: 'Charles Mingus'  ⋄ year: 1959)
  (title: 'Head Hunters'              ⋄ artist: 'Herbie Hancock'  ⋄ year: 1973)
)

jazz.artist
Loading...
(1959=jazz.year)/jazz.title
Loading...

This also extents to ⎕VGET and ⎕VSET:

(1959=jazz⎕VGET'year')/jazz⎕VGET'title'
Loading...

We can construct some SQL-like helper operators here:

_Where_ ← {⍵ ⍵⍵ ⍺⍺ ⎕VGET ⍺}
_Select_ ← {⍵/⍺⍺ ⎕VGET ⍵⍵}
(jazz _Select_ 'title') 'year' (jazz _Where_=) 1959
Loading...

We can add a column to all member namespaces at once, as ⎕VSET happily takes array left arguments:

jazz ⎕VSET ⊂'genre' 'jazz'
⍪NSShow¨jazz
Loading...

Reference semantics¶

As we alluded to above, namespaces are references in Dyalog APL. This has some interesting consequences, such as mutation via ⍺ (or ⍵) in a dfn:

kob_ ← (title: 'Kind of Blue' ⋄ artist: 'Miles Davis' ⋄ year: 1959)

SetGenre ← { ⍺ ⎕VSET ⊂'genre' ⍵ }

kob_ SetGenre 'Jazz'

NSShow kob_
Loading...

References also lead to aliasing,

a_ ← (foo: 'bar')
b_ ← a_
b_ ⎕VSET ⊂'fee' 'baz' ⍝ Mutate `a_` via its `b_` alias

NSShow a_
Loading...

which is a behaviour we don’t see with values:

a ← 1 2 3 4
b ← a         ⍝ Copy
b ,← 99

a
Loading...

It’s easy to slip up here. Take a look at this:

(b_ a_) ← ⎕NS ⍬
a_.foo ← 'bar'
b_.foo ← 'baz'

(a_ b_).foo
Loading...

What happened there was that we created a SINGLE namespace reference, which then got scalar-extended to the two variables a_ and b_ -- with b_ now aliasing a_.

Dyalog APL has several reference types, also including objects (closely related to namespaces). Mutable references have a tendency to add “spice and excitement” to your code, so use wisely.

If you do want value semantics for namespaces, you need to “deep clone” them. ⎕NS can take a namespace right argument, in which case it will return a deep clone:

a_ ← (foo: 'bar')
b_ ← ⎕NS a_            ⍝ `b_` is a deep clone of `a_`
b_ ⎕VSET ⊂'fee' 'baz' ⍝ Mutate `b_` only

⍪NSShow¨a_ b_
Loading...

We can use the cloning facility of ⎕NS to merge namespaces, which gives us a neat way of implementing progressive defaults. ⎕NS can take any number of namespaces to the right, and return a new namespace which is the union (with last-wins replacement):

defaults_ ← (role: 'Drummer' ⋄ name: 'None given')
person_ ← ⎕NS defaults_ (name: 'Baard Kolstad')
NSShow person_
Loading...

Namespaces as namespaces structured containers for code¶

The other aspect of Dyalog APL namespaces is as a code container construct -- an actual namespace. In its simplest form, it requires but a small mental leap: values in a namespace can be functions as well as arrays:

ns_ ← ()

ns_.Sum ← +/

ns_.Sum ⍳100
Loading...

In this form, if you squint a bit, a Dyalog APL namespace start to resemble a JavaScript object. We can mock up the beginnings of a maths utility library:

math_ ← ()
math_.Abs ← |
math_.Cos ← 2∘○
math_.pi ← ○1

math_.Cos math_.pi
Loading...

Sadly, we can’t (yet) write this as APLAN:

math_ ← (    ⍝ SYNTAX ERROR: Function and operator elements are not permitted (v21)
  Abs: |
  Cos: 2∘○
  pi: ○1
)
SYNTAX ERROR: Function and operator elements are not permitted

but rumours are that this extension is on the roadmap for a future Dyalog release.

Dyalog relies extensively on this type of namespaces in pretty much all APL code it ships. Namespaces are one of the core mechanisms for modularity in APL code, but if you know more mainstream programming languages, some aspects will not work as you expect -- but that’s kind of true for APL in general, isn’t it.

Namespaces and variable scope¶

Namespaces and variable scope varies greatly between programming languages. Let’s illustrate a few scope gotchas. Here’s a contrived example implementing a counter:

counter_ ← (count: 0)
counter_.Increment ← {
    count +← 1               ⍝ I can see names defined in my own namespace
    count
}

count ← 100                  ⍝ Outer variable, lexically scoped

Demo ← {
    count ← 5                ⍝ Shadows the outer `count`
    _ ← counter_.Increment ⍬
    ⎕ ← count                ⍝ 5 -- inner scope wins
    ⎕ ← counter_.count       ⍝ 1 -- reached by named access
    ⍬
}

Demo ⍬
count                        ⍝ 100 -- never touched
Loading...
Loading...

That was hopefully what you expected to see. What if we add another layer of namespace nesting?

counter_ ← (count: 0)
counter_.(inner_ ← ())
counter_.inner_.Increment ← {
    count +← 1                ⍝ VALUE ERROR: Undefined name: count
    count
}

counter_.inner_.Increment ⍬
VALUE ERROR: Undefined name: count
Increment[1] count+←1                ⍝ VALUE ERROR: Undefined name: count
                  ∧

If that was what you expected to see, well done -- another deep insight. In other words, in Dyalog APL, namespaces are NOT lexical scopes. In order for the inner_ namespace to see names defined in its enclosing namespace, we must reference those explicitly:

counter_ ← (count: 0)
counter_.(inner_ ← ())
counter_.inner_.Increment ← {
    ##.count +← 1
    ##.count
}

counter_.inner_.Increment ⍬
Loading...

The ##. thing means “...in the enclosing namespace”. Note that the following does NOT work:

counter_ ← (count2: 0)
counter_.inner_ ← ()            ⍝ Careful...
counter_.inner_.Increment ← {
    ##.count2 +← 1                
    ##.count2
}

counter_.inner_.Increment ⍬
VALUE ERROR: Undefined name: count2
Increment[1] ##.count2+←1
                      ∧

Why? The key is the lack of parentheses in counter_.inner_ ← (). This does not create a new namespace in the counter namespace under the name inner_, it creates a namespace (reference) in the root namespace, and aliases that as the name inner_ in the counter_ namespace.

A single # refers to the global root namespace, and ⎕THIS returns a reference to the current namespace. With that knowledge at hand, try to explain the following behaviour:

(foo←{⎕THIS})⍬

(⎕SE.foo←{⎕THIS})⍬

⎕SE.foo⍬
Loading...
Loading...
Loading...

⎕SE is the SEssion namespace, a place where various system-y things get loaded on startup. The last two invocations call the exact same instance of the foo function; they ought to return the same thing, but they don’t. Bug or feature?

Named namespaces¶

So far, we’ve created anonymous namespace references on the fly, primarily via the () APLAN convenience. There are several other ways to create namespaces. We can create named namespaces instead of anonymous references:

⎕ ← 'bar_' ⎕NS ⍬
Loading...
ns_ ← ()
⎕NC 'ns_'
⎕NC '#.bar_'

Namespaces as nested workspaces¶

We started this chapter with an admittedly poor attempt at a joke, dissing Dyalog’s claim that

Namespace is a (class 9) object in Dyalog APL. Namespaces are analogous to nested workspaces.

as somewhat opaque. However, it’s worth exploring. We’ve glossed over the “workspace” concept at best so far, partly because it’s a model that doesn’t really appear much in today’s mainstream development environments. We can think of a Dyalog APL workspace as a binary snapshot containing your defined functions and variables etc. This is a concept that’s been part of APL implementations since its inception. It has some seductive qualities: as a binary snapshot, it’s easily frozen in time and distributable. It has little start-up cost. It Just Works Everywhere. Workspaces used to be completely flat, with zero structure, and at some stage, someone decided that it would be helpful to have the ability to impose some structure. Namespaces are one solution to this -- and understanding how namespaces can be seen as nested workspaces helps in also understanding why the scoping rules are what they are.

Binary workspaces, of course, have drawbacks, too -- which is why we rarely see them outside APL (and Smalltalk) today. In 2026, programmers expect to be able to store their source code as textfiles in a versioning system, like git. That’s potentially awkward in a workspace-oriented paradigm. Dyalog’s Link is a response to this: it maps a directory of source files into a Dyalog APL workspace as a set of nested namespaces. We’ll discuss Link in a later chapter.

Without a great leap of imagination, we can think of a workspace with nested namespaces as conceptually similar to a hierarchical filesystem with # representing the root. We can use the system function ⎕NL (Name List) a bit like ls -- it lists the various objects present in the namespace in which it’s being run, of the type given by its right argument:

⎕NL 2 ⍝ List variables (name class 2)
Loading...

The constants for Dyalog’s name classes can be scrutinised on the documentation page for ⎕NC, but the pertinent set we’re interested in is

Name ClassDescription
¯1invalid name
0undefined name
1Label
2Variable
3Function
4Operator
8Event
9Object (GUI, namespace, COM, .NET)

This works for nested namespaces, too. Let’s add some more bits to our burgeoning math_ namespace:

math_.e ← 2.718281828459045235360287471352
math_.Mandel ← {⍉' *'[2>|{k←2>|⍵ ⋄ (⍵×~k)+k×c+(⍵×k)×⍵×k}⍣⍵⊢c←¯2.1J¯1.3+((2.6÷b-1)×¯1+⍳b)∘.+0J1×(2.6÷b-1)×¯1+⍳b←51]}
math_.Mandel 150
Loading...
math_.⎕NL 2 ⍝ Variables (2)
math_.⎕NL 3 ⍝ Functions (3)
Loading...
Loading...

Working in the interactive session, we can change the “working directory” -- the current namespace -- with the Change Space (⎕CS) system function, analogous to the cd shell command you use every day:

⎕NL 3 ⍝ Current namespace is #
Loading...
⎕CS 'math_' ⍝ Move into the `math_` namespace
⎕NL 3 ⍝ Current namespace is now #.math_
Loading...

In fact, nested namespaces map very closely to a filesystem -- almost every common filesystem operation has a corresponding namespace operation, with cd mapping to ⎕CS, ls to ⎕NL and so on.

With the filesystem metaphor in mind, it’s perhaps clearer why name resolution in nested namespaces doesn’t walk the scope chain. It would be very confusing if you typed

% cat myfile

in your terminal and you’d see the content of a file that lived several directories above the one you’re in. The filesystem has a “parent pointer”: ../ mapping to a Dyalog APL namespace’s ##. for when you do need to explicitly reference something “above” your current nesting depth.

Scripted namespaces¶

With namespaces capable of containing both data (including other namespaces) and functions, we can also think of them as a kind of object instance. In fact, Dyalog APL’s object-orientation features, which are deliberately out of scope for this book, are really built atop namespaces.

We haven’t covered how to load APL programs from textfiles yet, but namespaces can be used as building blocks for keeping code and data co-located, source-wise, without going “full O-O”. For now, type

)ed ⍟str_

Yes, that of course is the glyph for logarithm -- how else would an APLer choose to create a scripted namespace? Type the following in the tab that emerges:

:Namespace str_

    Lower ← ⎕C
    Upper ← 1∘⎕C
    Strip ← ' '∘(1↓,⊢⍤/⍨1(⊢∨⌽)0,≠)
    StartsWith ← ⊢≡↑⍨∘≢
    EndsWith ← ⊢≡↑⍨∘-∘≢
    Find ← ⍸⍷
    Split ← ≠⊆⊢
    Join ← 1↓∘,,⍤0

:EndNamespace

To save and evaluate your namespace, hit Esc -- because of course escape sounds just like “save” to an APLer. If that wasn’t obvious to you, don’t worry. There is really no way to discover this except by being told. We’ll look into a sane setup for Ride in a later chapter.

We now have the beginnings of a port of Python’s string utilities:

(str_.Lower 'HELLO WORLD') str_.StartsWith 'hel'
Loading...

You’ll see and hear some APL legends talk about how libraries often aren’t needed in APL, and how the DRY principle doesn’t apply. “Idioms, not libraries”. Code re-use by cut and paste is a virtue, not a sin, the saying goes.

You can certainly see where that kind of thinking comes from. Compare:

' ' (≠⊆⊢) 'Idioms not libraries'
' ' str_.Split 'Idioms not libraries'
Loading...
Loading...

In a language as terse as APL, phrases like ≠⊆⊢ for split are already shorter than any reasonable naming, and soon becomes parsed as a single unit to the human eye. It’s worth bearing in mind as you progress -- don’t name things that don’t need a name.
