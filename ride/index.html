Ride

Keats and Yeats are on your side / While Wilde is on mine. --Morrissey Morrissey, 1986

Ride started life as a Microsoft Silverlight application, and was intended to become the one Ring IDE to rule them all, in terms of Dyalog’s supported platforms. It didn’t turn out that way. It was since rewritten in JavaScript, as an Electron app and is an open source project. Ride’s using the Monaco editor component that also powers VS Code.

Ride has two distinct roles, sometimes conflicting. On the one hand, it’s used to attach to remote, running instances of Dyalog to facilitate debugging of running applications. On the other hand, it’s the default IDE that non-Windows users use to develop Dyalog APL locally on their computers. As the “non-Windows users” segment of Dyalog’s user base has always been comparatively small, Ride occasionally feels not entirely comfortable on macOS or linux. Especially on macOS, it doesn’t always respect the established OS conventions, particularly when it comes to how it handles multiple windows.

The reason it’s like this is that the “classic” model for the Windows IDE is that it opens separate floating windows for everything, and this doesn’t really fit with the application model of Electron -- or indeed macOS, for that matter. If you’re a classic-mode Dyalog user on Windows and you need Ride to debug a remote session, the model feels comfortable, and this is the root of the uncanny valley that makes Ride feel a bit awkward. Multiple sessions in Ride are completely separate application processes, and on macOS, you’ll then see many Ride icons in your dock, instead of a single icon which gathers its session windows like you’d probably expect.

Other issues -- that we can partly address -- are for example the out of box configuration settings that are both hard to discover and not set to the expected platform defaults. The other aspect is the philosophy: Ride looks much like any other editor/IDE you will be familiar with, but is better seen as a “dumb” display tool. It delegates everything to the interpreter, including the state of windows and tabs. It reflects the workspace model of Dyalog APL. It has no concept of “files”, or “save/open/close” in the ways you expect. Without Link, which we met earlier, using Ride would be a pretty tiresome experience to me. Once we understand the workspace model, and how Link maps this to the file system, we can begin to make the most of Ride. And don’t get me wrong -- these issues really are paper cuts, not deal breakers.

We’ve talked about workspaces and Link already. Let’s dwell a bit on the session interface -- in Ride specifically, but coming back to the “dumb display tool” idea, is actually mostly the interpreter itself dictating the behaviour. The session is really an active canvas, and does not at all behave like the shell interface it looks like. If you expect to be able to use the arrow keys to recall your session history, you’ll be surprised to see that instead it moves the cursor up and down your previous output. If you press return, it tries to re-execute whatever line you happen to be on -- including lines that cannot be executed. This plays badly with boxed output, and the beginner will frequently end up in a state like this:

A long, boxed output, and you tried moving up a few lines and pressed return, expecting shell behaviour, but got a canvas. Perhaps you then tried to clear the screen from all the junk output with a ctrl-l, but that had no effect. The ability to re-evaluate lines in the output flow is something APLers love and see as a feature. It takes a while to adapt to, if you used to normal editors, shells and REPLs. You can, of course, also go up and down your session history, just not with the arrows, by default. Instead, you use ctrl-shift-backspace for up, and ctrl-shift-enter for down. That’s worth committing to memory immediately.

Let’s look at some quality of life configuration changes. Click on the little keyboard symbol in the top right to open Ride’s preferences settings, and select the Shortcuts tab. You should see something like this:

This tab lets you view, modify and create new keyboard bindings. First, in the search box, type FX, Dyalog-speak for what the rest of the world would think of as Save. Click the little + symbol, and enter the key-combo that corresponds to your operating system’s standard for Save -- on macOS, ⌘s. Click APPLY. Next, search for SI (Strong Interrupt), and set that to ctrl-c.

It’s worth botanising a bit in this window -- a lot of functionality is only available on shortcuts that have no default key setting, and some have cryptic names to boot.

With FX bound to your key-combo of choice, you can now open an edit window, and save it in place, keeping the editing window open. Try

)ed foo

See the little black circle in the tab title bar? That means that the contents are not saved/fixed. Press your new key combo, and note how the circle gives way to a cross (for close window).

Note

Fixing a function does not save it to disk, it “compiles” it and makes it available in the current workspace. To save your function to disk, you need to have linked your workspace.

Namespaces, classes...¶

When you typed )ed foo, Ride (or actually, the interpreter) expects you to edit a function. It does not examine the editor contents to see what you actually wrote. Yes, if you think that’s weird, that’s because it is weird. It exposes a conundrum -- what if you want to create something that isn’t a function, like a scripted namespace? That sounds like a job for a logarithm. No joke.

)ed ⍟MyNamespace

will open an editor window pre-populated with

:Namespace MyNamespace
:EndNamespace

and the interpreter expecting a namespace. There are more magic symbols (of course), but we’re not too concerned with them in the context of this book. For completeness

)ed ∘MyInterface
)ed ○MyClass

Tracing¶

Ride has excellent debugging capabilities built in (or to be precise about it, the Dyalog APL interpreter has excellent debugging capabilities that Ride taps into), again, just hard to discover. The debugger -- or tracer as we call it in APL -- has several tricks up its sleeve you might not be familiar with, like stepping backwards, modifying code mid-trace and skipping lines, all of which are made possible by the dynamic nature of the language and its implementation in the interpreter.

One way to start tracing to to by setting a breakpoint in the edit window on some line where we want execution to pause. Click in the left gutter at the beginning of the line, and you should see a red dot appear:

Running the function should now pause on the break-pointed line and open the tracing pane, with a tooling icon strip that should be familiar to you from other debuggers you’ve come across:

Note that at this point, the session is live in the stack frame where we’ve paused. You can interact with the state that the function can see at this point in the execution, including redefining variables:

Hovering over names in the tracer pane shows values as tool-tips:

We don’t even need to set a break point in order to start tracing. There is another key stroke worth remembering, Trace Line (TC), by default set to ctrl-enter that you can apply to an expression in the session to start evaluating it under tracer control.

We can also step through individual phrases, glyph by glyph, referred to as Inline Tracing, which can be supremely useful, especially when examining tacit expressions. You can enter inline tracing via the IT key stroke, defaulted to ctrl-alt-enter. Note the little red box around the ⍳, indicating the next function to be evaluated:

Repeated ctrl-alt-enter moves us along the execution. Here’s a video showing a simple example of stepping through a tacit expression:
